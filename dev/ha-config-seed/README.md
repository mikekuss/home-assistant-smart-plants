# Home Assistant Development Seed

This directory is the committed starting state for the isolated local Home Assistant development instance. `scripts/ha-up.ps1 -Expose` (or `ha-up.sh --expose`) copies its contents into the gitignored `dev/ha-config/` runtime directory on first use.

Contrary to a stock HA install, the seed is **pre-onboarded**: cloners boot straight into a signed-in owner account with Smart Plants already added. This is a deliberate DX call for a loopback-only development rig — the alternative was making every clone and every reset click through onboarding.

## Login

- Owner: `admin`
- Password: `admin`

The bcrypt hash for `admin` lives in `.storage/auth_provider.homeassistant`. This is acceptable **only** because [docker-compose.ha.yml](../../docker-compose.ha.yml) publishes the rig on `127.0.0.1`, so the login is unreachable from other machines. With `-Expose` / `--expose` the port stays loopback-only, but the container gains outbound internet/LAN access. Do not reuse the seed against a container that publishes on `0.0.0.0` or on any non-loopback interface.

## Security Rules (still in force)

- Never point this rig at real actuators, real OpenPlantBook tokens, HACS credentials, or any live Home Assistant data.
- Never expose the container beyond `127.0.0.1`.
- Do not commit refresh tokens or session cookies. The regen script refuses to write the seed while `.storage/auth.data.refresh_tokens` holds a session token, so log out of every session before stopping the rig. It removes Home Assistant's system content user, whose token cannot be logged out, and never seeds `.storage/http.auth`.
- Do not add new integrations whose config entries would embed API keys or personal identifiers into `.storage/core.config_entries` when regenerating the seed.

## Seed Contents

- `configuration.yaml` — logging, short recorder retention, and synthetic plant-adjacent sensors.
- `.HA_VERSION` — pinned to the container image version. HA refuses to boot a seed newer than the image.
- `.storage/auth`, `.storage/auth_provider.homeassistant`, `.storage/person`, `.storage/onboarding` — seeded owner + onboarding-complete marker.
- `.storage/core.config_entries`, `.storage/core.device_registry`, `.storage/core.entity_registry`, `.storage/core.area_registry` — Smart Plants integration registered as a loaded entry.
- `.storage/core.uuid`, `.storage/http`, `.storage/homeassistant.exposed_entities`, `.storage/lovelace_dashboards`, `.storage/lovelace.map` — identity and default UI wiring.

Everything else (SQLite DB, logs, `deps/`, `blueprints/`, `tts/`, restore-state cache, run lock) is runtime state and is regenerated by HA on first boot — do not commit it.

## Regenerating the Seed

The seed goes stale in two situations. Both require a regen:

1. **Home Assistant version bump.** When you change the pinned image in [docker-compose.ha.yml](../../docker-compose.ha.yml), HA may migrate `.storage/` schemas on first boot. The committed seed then no longer matches the new image on clean clones.
2. **Smart Plants schema or model change.** Anything that touches `custom_components/smart_plants/storage.py`, `config_flow.py`, `const.py::DOMAIN`, entity unique IDs, or the config-entry version/minor_version can invalidate the seeded `core.config_entries`, `core.entity_registry`, or our own `.storage/smart_plants.*` blobs once we add them.

Procedure:

```powershell
./scripts/ha-reset.ps1               # wipe dev/ha-config/
./scripts/ha-up.ps1 -Expose          # boot bare rig against the new image / new code
# Complete onboarding as admin / admin, add Smart Plants, add any demo data desired.
# Log out of every session so no refresh token is left.
./scripts/ha-down.ps1                # stop so .storage/ flushes cleanly
./scripts/ha-seed-from-runtime.ps1   # check and copy curated files back into dev/ha-config-seed/
git status --short dev/ha-config-seed # inspect every candidate file
git diff -- dev/ha-config-seed        # review tracked-file changes
```

Bash equivalents: `ha-reset.sh`, `ha-up.sh --expose`, `ha-down.sh`, `ha-seed-from-runtime.sh`.

The regen script runs `scripts/seed_guard.py` on the copied files and leaves this directory untouched when it finds a problem: a UTF-8 byte order mark in any file, a refresh token, an owner password hash other than the committed `admin` one, non-empty `smart_plants` config entry `data` or `options`, devices with connections, serial numbers, or from new integrations, or new areas. See [local-ha-testing.md](../../docs/development/local-ha-testing.md#seed-guard) for details.

If the regen script errors out because HA's `.storage/` grew a new keyfile that we should include (or should exclude for privacy), update the `StorageKeep` list in both `ha-seed-from-runtime.ps1` and `ha-seed-from-runtime.sh` and rerun.

Never use a broad `git add` for this directory. Verify refresh tokens are empty
and stage only each reviewed allowlisted file by its explicit path.
